# Deployment changes and handoff

Implementation of [DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md). Nothing has been
pushed, published, or applied to a cluster as part of this work.

## Repository layout

The existing `infrastructure/argocd` directory is in the separate infrastructure
repository. It owns the shared platform and the Argo CD child Applications.
This assignment repository owns the application workloads under `deploy/base`
and `deploy/overlays/production`, matching the plan. The infrastructure checkout
already contains a `quad-assignment` child Application pointing at this overlay,
plus the platform-validator change for this external repository. Those files
were inspected and left untouched.

`deploy/argocd-application.yaml` is a reference for that infrastructure-owned
Application. It is not included in the assignment's rendered overlay.

## Implemented changes

| Area | Change |
| --- | --- |
| Backend build | Disable Quinoa in production; keep it in development. Export OpenAPI independently to `target/openapi`. Keep Java 25 packaging and `/api`. |
| Health | Add SmallRye Health on internal management port 9000. Readiness checks PostgreSQL; liveness remains independent of database availability. |
| Frontend image | Build with Node 24.19.0, `npm ci`, and the exported schema. Serve static output with unprivileged Nginx on 8080, including SPA fallback. |
| Browser URLs | Serve assets and routes from `/`. Generate same-origin `/api/...` calls using Vite's `import.meta.env`; remove the localhost API fallback. Proxy `/api` in local Vite development. |
| Manifests | Add separate frontend/backend Deployments and ClusterIP Services, resources, probes, non-root users, and disabled service-account token mounting. |
| Database | Add one CloudNativePG PostgreSQL 17 instance with a pinned multi-architecture image, a 1Gi persistent volume, and operator-generated credentials. Preserve startup migrations. |
| Routing | Reuse the existing public Gateway, namespace/DNS labels, wildcard HTTPS listener, and hostname `quad.dylannas.nl`. |
| Data protection | Order namespace/database/application sync waves and protect namespace/database against pruning and Application-driven deletion. |
| CI | Validate builds and manifests; smoke-test runtime images; publish ARM64 and AMD64 images only from `main` after checks pass. |
| Release approval | A GitHub App opens or updates one deployment PR containing both image digests. Dylan reviews and merges it. No direct image-update commits to `main` or automatic merges. |
| Loop prevention | Deployment-only changes validate manifests without rebuilding images or generating another deployment PR. |

## Additional fixes found during verification

- TypeScript 6 rejected the existing `baseUrl` settings. Removed them and made
  the `@/*` alias targets explicitly relative in both TypeScript configurations.
- The page imported an ignored `src/generated/index.ts` file that was present
  locally but not generated by Orval. Changed imports to the actual generated
  endpoint modules and enabled cleaning of generated output so fresh builds do
  not rely on stale files.
- Corrected the existing unsupported Quinoa logging property to
  `quarkus.quinoa.dev-server.logs`.
- Expanded `.dockerignore` so the frontend Docker build can access its source
  and exported schema while excluding local dependencies and environment files.
- Checked registry manifests directly and pinned the PostgreSQL **image index**
  digest, which contains both AMD64 and ARM64 images.

## Configuration still needed before pushing/deploying

1. Create GitHub Actions secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`, with
   write access to both `kurza/quad-assignment-*` image repositories.
2. Install a deployment GitHub App with Contents and Pull requests read/write
   permissions. Add its ID as variable `DEPLOYMENT_APP_ID` and its PEM private key
   as secret `DEPLOYMENT_APP_PRIVATE_KEY`. Keep its identity separate from Dylan's.
3. Allow bot branch updates and PR creation in repository/organization settings.
   Protect `main` with review requirements and the `manifests` check.
4. Confirm the production CloudNativePG operator/CRDs and suitable default
   StorageClass are healthy. Set `spec.storage.storageClass` explicitly if the
   default is unsuitable or absent. Verify PVC provisioning before starting the
   application workloads.
5. For private Docker Hub repositories, separately provision a pull Secret and
   reference it from both Deployments. For a private Git repository, configure
   Argo CD read access.
6. After those settings are ready, push/merge the implementation to `main`.
   Review and merge the first generated deployment PR. The initial all-zero SHA
   image tags are bootstrap placeholders and must be replaced before enabling
   Argo CD reconciliation for this application.
7. Coordinate the infrastructure-repository Application change separately.
   Keep pruning disabled and omit a cascading-deletion finalizer. Complete the
   production acceptance checks after the first sync.

The full commands, rollout sequence, and rollback guidance are in
[deploy/README.md](deploy/README.md).

## Verification and limits

- Backend `clean verify` passed with Quinoa disabled and fresh OpenAPI output.
  The local JDK is 26 and compiles with release 25; CI explicitly uses JDK 25.
  There are no existing Java tests in this repository.
- A clean `npm ci` and the frontend production build passed. The browser bundle
  check verifies root assets and API paths, no localhost API target, and no
  unguarded dependency on Node's `process` global.
- Rendered production manifests passed the deployment validator.
- GitHub Actions workflow passed `actionlint`; the smoke script passed Bash
  syntax validation. The image updater was checked with both bootstrap tags and
  existing digest references.
- Registry inspection confirmed ARM64 and AMD64 support for the runtime/build
  images used by the deployment.
- Docker is not running locally, so runtime container smoke tests have not been
  executed here. They are included in CI before publication. The active local
  Kubernetes context is unrelated to production; operator health, actual node
  architecture, storage provisioning, Gateway acceptance, and browser quiz flow
  still require verification in the production cluster.
